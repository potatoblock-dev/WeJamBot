# 设计取舍

这份文档记录**为什么是现在这个形态**。每条都对应一个踩过的坑。

## 不用 OCR：无障碍树本来就有结构化文本

微信 Linux 版基于 GTK + Chromium，默认向无障碍总线暴露完整节点树。会话列表与消息正文都是现成文本：

```
[list] '会话'
  [list item] '文件传输助手\n剪贴板方案验证：中文、标点，以及 emoji 🚀 都试试\n13:32\n'
[list] '消息'
  [list item] '13:32'
  [list item] '剪贴板方案验证：中文、标点，以及 emoji 🚀 都试试'
```

对比 OCR 方案：同一条消息要识别、要纠错、要处理中英文混排与 emoji；现在是直接读字符串。

:::tip 需要一处开关
GTK 的无障碍桥默认关着。镜像里编译了一份 gschema override 打开
`org.gnome.desktop.interface toolkit-accessibility`，
并给微信进程设 `ACCESSIBILITY_ENABLED=1`。

踩过的坑：`glib-compile-schemas`（属于 `libglib2.0-bin`）没装的话，
override 会**静默失效**；而且没有 `gtk-modules` 这个键，正确的键是 `toolkit-accessibility`。
:::

## 输入：剪贴板粘贴为主，键码重映射兜底

宿主的输入法（fcitx5 / ibus）会劫持合成按键：实测输入 `WeJamBot virtual-display loop OK`
变成了 `W呃J按摩B呕吐virtualdisplayloopOK` —— 拼音候选把空格和回车都吃掉了。

容器里的会话总线不连宿主，从根上断掉劫持。至于往输入框里放文字，走**两条路**：

**主路：剪贴板粘贴**（`xclip` 写入 → Ctrl+V）

| 好处 | 说明 |
|---|---|
| **支持多行** | 逐字符注入时 `ord('\n')` 就是 Return，而 Return 在微信里是「发送」—— 多行会把前半句直接发出去 |
| **恒定耗时** | 粘贴约 0.5 秒，与长度无关；逐字符注入是 19ms/字，500 字要 9.5 秒 |

:::tip 为什么不必担心「污染用户的剪贴板」
本工具是**容器原生**的：容器里的 Xvfb 有自己独立的剪贴板，跟宿主完全隔离，
也没有剪贴板管理器。只有「不跑容器、直接占用宿主 X」才会碰到用户剪贴板 ——
而那种部署方式本身比这粗暴得多，正是设计要避免的。
:::

**兜底：键码重映射**（把空闲键码临时映射成目标 Unicode keysym）

不依赖 `xclip`，也不依赖剪贴板内容。中文与 emoji 都能直接打进去，不经过任何 IME。
代价是慢（19ms/字），而且**无法输入换行**，所以只在剪贴板路径失败、且文本是单行时才用。

无论走哪条路，打完都**回读输入框比对** —— 注入可能静默丢字，不校验就等于赌。

## 零静态坐标：比例映射

无障碍节点的 extents 用的是 GTK 逻辑像素，和 X11 物理像素之间存在**未知缩放**
（实测 96/100），而且改 DPI 之后尺寸仍不一致 —— 不能靠单一公式建模。

所以用**归一化比例**：

```
rel_x = (node.x - frame.x) / frame.w      # 0..1，与缩放无关
phys_x = win.x + rel_x * win.w            # 套到 X11 窗口真实几何上
```

弹出层（菜单、设置面板）是独立窗口，其节点**没有 frame 祖先**，
这时退回全局仿射变换兜底。两条路都不含坐标常量。

## 服务持有状态，客户端只消费

```
┌─ 容器 ────────────────────────────┐
│  Xvfb + 微信 + AT-SPI             │
│  agent：登录状态机 + gRPC 服务     │
└──────────────┬────────────────────┘
               │ 契约
┌──────────────▼────────────────────┐
│  宿主：任意语言的 gRPC 客户端      │
└───────────────────────────────────┘
```

契约只描述**能力**与**状态**，不描述**手段**。a11y / XTEST / 截图 / 坐标这些词
不出现在契约里，也不该出现在客户端代码里。

二维码就是个例子：服务在容器内解码，只把**内容字符串**送出来，渲染由客户端决定 ——
这样 headless CLI、AI agent、无图形环境的客户端都能用。

## 一切界面操作串行化

界面 / X server / pyatspi 的 D-Bus 连接，本质上都是**单线程资源**。
而 agent 里有多条并发路径：gRPC 线程池（默认 8 个 worker）+ 登录轮询线程。

不加锁的后果实测过：并发发消息时键码交错，消息变成乱码。
现在所有「读界面 / 动界面」都走 `agent/ui.py` 的全局 RLock。

:::warning 一个反直觉的细节
登录轮询**不能**整体持锁 —— 它每轮要走整棵无障碍树（约 1 秒）而每秒跑一次，
整体持锁会把所有 RPC 饿死。所以它**只在「点击」那一步持锁，并在锁内重新定位节点**，
保证点的是当下真实位置。
:::

## 验证而非假设

| 位置 | 假设会怎样 | 现在怎么做 |
|---|---|---|
| 发送消息 | 打完回车就当成功 | **回读输入框**确认已清空，否则重试并如实报错 |
| 读取消息 | 固定 sleep 等渲染 | 轮询到连续两次条数一致才算稳定 |
| 监听增量 | 打开会话就算基线 | 会话切换进稳定期，避免把渲染中的历史当成新消息 |
| 消息去重 | 用列表序号做 ID | 序号会随滚动漂移 → 改用「时间桶 + 正文 + 出现次序」 |

## 危险操作要有防线

:::danger 曾经误触过「退出登录」
盲点代码点到了设置面板里的「退出登录」，弹出模态框挡住后续所有操作，
而工具自己毫无察觉。现在：

- **危险按钮黑名单**：`退出 / 注销 / 清空 / 删除 / 撤回 / 解散` 一律拒绝点击
- **弹层防护**：见下
:::

### 弹层防护：点击会打到最顶层窗口

点击坐标是按无障碍节点算出来的，但**弹层（菜单 / 对话框 / 设置面板）是独立窗口且盖在上面**，
X 会把点击投递给最顶层窗口 —— 于是「点会话列表」实际打到了弹层上的某个位置。

这不是猜测：实测中就是从设置面板里点到了「退出登录」，弹出确认框后又**挡住了后续所有操作**。

所以现在每次操作前都要确认界面处于「只有主窗口」的已知状态：

```
有额外窗口？ → 先按 Esc 尝试关闭 → 仍然有？ → 放弃操作并如实报错
```

### 服务不该自主导航界面

版本探测原本会走「设置 → 关于微信」读版本号 —— 这属于**自主导航**，
而它带来的收益（一个版本字符串）远不值得冒误触的风险。

现在版本默认只从 `dpkg` 或进程参数读（**零副作用**），
GUI 探测默认关闭，仅在显式设置 `WEJAM_VERSION_VIA_GUI=1` 时启用。

### 绝不允许「静默返回错误结果」

同类问题的第三种形态：`messages(chat=X)` 在打开 X 失败时，会**把当前会话的消息
贴上 X 的名字返回**。调用方据此操作，就可能在错误的会话里发消息。

现在一律抛错（gRPC 侧映射成 `FAILED_PRECONDITION`），宁可失败也不给错数据。


## 独立聊天窗口：别让自己的守卫把功能关掉

微信允许把会话开进**独立窗口**（右键会话 → 「独立窗口显示」）。会话常驻之后，
对它读/发都不再有切换开销：实测 **0.9~1.8 秒**，而需要切换时是 **4.8~7.7 秒**。

我第一版做完后测出「同时只能开 1 个独立窗口（开新的会替换旧的）」，
还把这个「限制」写进了文档。**但那是假的**，是我自己两个 bug 造成的：

**bug 1：弹层守卫把独立窗口当成挡路弹层**

`_foreign_windows()` 的定义是「除主窗口外所有可见窗口」——
独立聊天窗口当然也在里面。于是每次操作前 `_popup_guard()` 都按 Escape 把它关掉。
表现出来就是「只能开一个」，实际是自己的守卫在关它。

修法：用 `pair_frames_with_windows()` 把「a11y frame 名字不是『微信』」的窗口
识别为合法的独立聊天窗口，从弹层候选里排除。

**bug 2：右键点到了盖在上面的独立窗口**

独立窗口会盖住主窗口的会话列表区域（独立窗口 x=328~951，会话列表项 x≈245~495）。
不把主窗口抬到最前就右键，点击会被投递给盖在上面的独立窗口，菜单根本弹不出来。

修法：点主窗口的控件前先 `raise_window(主窗口)`。

:::warning 教训
一个「能力不支持」的结论，有可能只是**自己的代码在阻止它**。
在把限制写进文档之前，先排除「是不是我干的」—— 这次的守卫就是我自己写的，
它尽职地把合法窗口也清了。
:::


## 虚拟桌面：窗口位置和屏幕尺寸都是我们自己定的

这是虚拟显示（Xvfb），不是物理显示器。屏幕多大、窗口摆哪儿、多大，
**全是我们自己的选择**。我一开始却当成物理屏在用 —— 1280×900、窗口随便叠，
结果一路踩坑：

| 症状 | 真正的根因 |
|---|---|
| 「点独立窗口里的头像」莫名打开了别的会话 | 点击被投递给**最顶层窗口**，而主窗口盖在上面 |
| 查发送者返回 `'动画表情'`（消息正文）或 `'公众号'`（别的会话名） | 资料卡的矩形**盖住了下面的列表**，按矩形取文本就读到了被压住的内容 |

我一度去改提取算法（按 frame 归属过滤、排除 list item…），单窗口下能跑，
多窗口下依旧不稳。**真正的修法是把窗口摆开、不让它们重叠。**

`windows.arrange()` 把主窗口和所有独立聊天窗口横向平铺：

```
主窗口 52% 宽  |  聊天窗口  |  聊天窗口  …
```

平铺之后同一套提取逻辑 **4/4 全对**，而且正确区分出同一群里的不同发送者
（`克里斯蒂娜` / `Fakefish 6.30`）。

屏幕尺寸也是可配的（`WEJAM_SCREEN`，见 `docker/entrypoint.sh`）：
能平铺几个窗口，取决于屏幕有多宽。

### 多指针（MPX）：机制在，注入路径缺

先纠正我说错的一句：**MPX 是 XInput 2.0 就有的**（master/slave 层级就是为它设计的），
不需要 2.1。实测在这个容器里创建第二个 master 设备**成功**：

```
$ xinput create-master wejam-second
⎡ wejam-second pointer    id=8   [master pointer  (9)]
⎣ wejam-second keyboard   id=9   [master keyboard (8)]
```

**每个 master 键盘有自己独立的焦点** —— 这正是「真并发写」缺的那一环。

但要走通还差两步，而且都不在 python-xlib 0.33 里：

| 需要 | 现状 |
|---|---|
| `XISetFocus` —— 给指定 master 设焦点 | `xinput` 没有这个子命令；python-xlib 未暴露 |
| `XTestFakeDeviceKeyEvent` —— 往指定设备注入 | XTEST 的 `FakeInput` 永远打到**第一个** master；python-xlib 只包了它 |

得手写两个原始协议请求。在此之前，「多窗口并发发送」仍然不可用。

:::warning 还有一个未验证的风险
`XSendEvent` 的实验表明**应用按自己内部的焦点状态路由按键**（事件投递地址被忽略）。
所以即使 X11 层面按设备分了焦点，微信/Chromium 是否跟着分，目前**没有证据**。
先把这点验证掉，再决定要不要投入实现那两段原始协议。
:::

## 一个隐蔽的定位 bug

角色匹配曾用子串：`find_node("list", "会话")` 因为 `"list" in "list item"` 为真，
会命中**正文里含「会话」二字的消息列表项**，导致 `ListChats` 静默返回空。

这类 bug 只在用户聊天内容恰好含该词时复现。现在改成**精确匹配优先、子串兜底** ——
既不会误命中，也保留了逃生舱接口写简写（`"button"` 配 `"push button"`）的便利。

## 可移植性

| 项 | 做法 | 原因 |
|---|---|---|
| 微信来源 | 官方 CDN 下载 `.deb` 装进镜像，`ARG WECHAT_ARCH` | 不依赖宿主已装微信 |
| 宿主 X | 不需要 | Docker Desktop 上不可能 |
| 网络 | 只 `-p 127.0.0.1:7700:7700`，不用 `--network host` | Desktop 上语义不同 |
| 状态 | 命名卷 `/data` | 与代码目录解耦 |
| 设备指纹 | machine-id 在卷里持久化 | 否则容器重建就要重新扫码 |
